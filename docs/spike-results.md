## 実行方法

```
mise exec -- pnpm install
mise exec -- pnpm run typecheck
TMPDIR=$PWD/.tmp mise exec -- pnpm test                                  # workerd 6 件 + e2e 15 件
cd packages/server && TMPDIR=$PWD/../../.tmp mise exec -- pnpm test:sandbox # Docker と github.com が要る。2 件
```

- `pnpm test` = `vitest run`（`@cloudflare/vitest-plugin` で workerd の中、`vitest.config.ts`）と `vitest run -c vitest.e2e.config.ts`（Node から本物の `wrangler dev` と本物の `prq` CLI を動かす）。e2e はファイルごとに `wrangler dev` を空の保存先で起動し、終了時に PID のプロセスグループごと止める（`test/e2e/support.ts:43`）。
- チャットのクライアントはブラウザーの `useAgentChat` ではなく、同じ WebSocket の手順（`cf_agent_use_chat_request` を送り、`cf_agent_chat_messages` / `cf_agent_use_chat_response` を受ける）を話す Node のクライアント（`test/e2e/support.ts` の `ChatClient`）。React の画面は作っていない。
- Access は本物ではなく、HS256 の JWT を `jose` で検証して代用した（`src/access.ts:14`）。service token かどうかは `common_name` の有無で分けた（`src/access.ts:23`）。本番は RS256 と `createRemoteJWKSet`。
- e2e は 3 回続けて全件通った（35〜45 秒）。

## 確認 2 と 6: local 担当の PrSession、`prq wait` / `claim` / `submit`、agent ID

注意点:

- **turn を起こさない方法:** local 担当では `onChatMessage` が `undefined` を返す（`src/pr-session/index.ts:84`）。SDK は警告のログ（`onChatMessage returned no response`）を出し、クライアントに本文 `"No response was generated by the agent."`、`done: true` のフレームを送る。トランスポートは JSON でない本文を捨てるので画面には出ない（`agents/dist/ws-chat-transport-*.js` の `sendMessages` を読んで確認、テストでストリーム本文が空であることを確認）。質問ごとに警告が出るのは本番の前に見直す。
- **local の質問のジョブ:** 送信が並ぶと、ある turn の時点で次の質問が既に保存されていることがある。そこで最後のメッセージではなく、ジョブの無いユーザーの質問すべてにジョブを作る（`src/pr-session/index.ts:95`）。
- **回答の位置:** `persistMessages` は会話の末尾に追加する。2 件待ちの後は「質問 1、質問 2、回答 1、回答 2」の順になる（テストで確認）。どの質問への回答かは回答の `metadata`（`jobId`、`target`）で UI が結び付ける必要がある。
- **在席:** 実装は「最後の接続（wait / claim / submit）から TTL 以内、または long-poll 中」。claim から submit まで TTL より長く接続が無いと在席から外れる（文書の「claim から submit までの間を在席」とは厳密には違う）。
- **同時の担当決定:** 最初の決定を残す（`INSERT OR IGNORE`、`src/pr-session/index.ts:59`）。
- **SDK の名前の衝突:** PrSession に `retry` というメソッドを作ると `Agent.retry` を上書きする（型検査で発覚）。`retryJob` にした。
- 未実装: 60 分で「止まっている」と表示すること（再試行の API `POST /api/session/:name/jobs/:jobId/retry` だけ作った）、`prq context` / `checkout` / `reconcile`、`skills/prq/SKILL.md`。

## 確認（クラウド担当、モックのモデル）

**判定: 動く（注意点あり）。**

| 確かめたこと | テスト（`test/e2e/cloud-owner.e2e.test.ts`） | 結果 |
|---|---|---|
| 送信で turn が走り、複数の `text-delta` でストリーミングされ、会話に保存される | "runs a model turn for a chat send and streams it to the client" | 通過 |
| webhook の分析を `waitUntilStable()` の後に関数の形の `saveMessages` で追加（`src/pr-session/index.ts:137`、`:148`）。A の分析中に B、質問、C が来ると、A → 質問 → C の順で走り、B は superseded | "runs webhook analyses with saveMessages after waitUntilStable…" | 通過 |

戻して落ちることの確認: 未着手の分析をまとめる処理（`src/pr-session/index.ts:118`）を外すと、このテストは B も走って落ちた。一方、`drainAnalysis` から `waitUntilStable()` を外しても通った。質問が先に処理されるのは、AIChatAgent の turn の待ち行列が到着順で、分析を 1 件ずつしか `saveMessages` に渡さないためで、`waitUntilStable()` はこの場面の決め手ではない（文書の規則どおり残してある）。

注意点:

- **会話の順序は保存の順:** 実行中の turn の間に送られた質問は、その turn の回答より前に並ぶ（「分析 A の依頼、質問、A の回答、質問の回答…」。テストで固定）。モックが「最後のメッセージ」を返すと前の回答を拾ったので、「最後のユーザーのメッセージ」に変えた（`src/pr-session/index.ts:86`）。本物のモデルでも、最後のメッセージが質問とは限らないことを文脈の組み立てで考える必要がある。
- `waitUntilStable()` が待つのは turn の待ち行列・保留中のツール・継続。関数の形の `saveMessages` と配列の形の違いは、このテストでは区別していない。

## 確認 5: GitHub App と webhook のライブラリ（workerd の中）

**判定: 動く（注意点あり）。`@octokit/auth-app`（JWT は内部で `universal-github-app-jwt`）と `@octokit/webhooks-methods` を使う。**

| 確かめたこと | テスト（`test/workerd/github.test.ts`） | 結果 |
|---|---|---|
| PKCS#1 の鍵（GitHub が配る形式）は拒否される | "universal-github-app-jwt rejects the PKCS#1 key GitHub issues" | エラー `Private Key is in PKCS#1 format, but only PKCS#8 is supported`（期待どおり） |
| PKCS#8 なら App JWT を作れ、公開鍵と `jose` で検証できる（RS256、`iss` = App ID、有効期間 10 分以内） | "universal-github-app-jwt signs a JWT…"、"@octokit/auth-app returns an app JWT…" | 通過 |
| installation token の取得: App JWT を付けて `POST /app/installations/42/access_tokens` を呼び、2 回目はキャッシュ（API は偽の fetch で代用） | "@octokit/auth-app gets an installation token…" | 通過 |
| `X-Hub-Signature-256` の検証: GitHub の文書の例（秘密 `It's a Secret to Everybody`、本文 `Hello, World!`、`sha256=757107ea…3e17`）と、違う署名・秘密・本文・`sha1=` の拒否 | "@octokit/webhooks-methods verifies GitHub's documented test vector"、"…rejects a wrong signature…" | 通過。例の値は node:crypto でも同じ値になることを確認 |

- 互換性の問題は 1 つだけ: `universal-github-app-jwt@2.2.2` は `#crypto` を Node では `crypto-node.js`、それ以外では `crypto-native.js`（WebCrypto、PKCS#8 のみ）に解決する（`package.json` の `imports`）。workerd は後者になる。回避は、鍵を一度 `openssl pkcs8 -topk8 -inform PEM -outform PEM -nocrypt -in app.pem` で PKCS#8 にしてから secret に入れること。手書きの JWT は要らない。
- wrangler のバンドルでも同じになるかは、`esbuild --conditions=workerd,worker,browser` でバンドルして WebCrypto 側だけが入ることを確かめた（wrangler の実際の条件の一覧は確かめていない。デプロイと dry-run はしていない）。
- webhook の検証は e2e でも `wrangler dev` の上の `/webhook` で使っている（`src/webhook.ts:17`。署名違いは 401）。

## 確認 4: Sandbox の作業場所（手元の Docker）

**判定: 動く（注意点あり）。数字は手元の Docker のもので、本番の値ではない。**

| 確かめたこと | テスト（`test/e2e/sandbox.e2e.test.ts`） | 結果 |
|---|---|---|
| 空から作り直す: `git init` → head と base を SHA 指定で深さ 1 で取得 → head を checkout → merge-base が無ければ深くする。停止して起動し直しても同じ SHA。停止の後は前のディスクが残っていない（`leftover: false`） | "rebuilds the same commit from empty after a stop, and runs grep and read in it" | 通過（3 周） |
| `git grep` と、`@cloudflare/sandbox` の `Files.readFile` で読む | 同上 | 通過 |
| git の通信は Worker の `GitOutbound` だけを通る: 同じ repo は通る、別の repo・別のホスト・http は 403 | "lets git reach only this repo on github.com through the Worker" | 通過 |

対象: `octocat/Hello-World`、head `b3cbd5bb`（branch test）、base `553c2077`（2 つ下の commit）。深さ 1 では merge-base が無く、1 回深くして見つかった。

計測（`test:sandbox` の 1 回の実行、ミリ秒）:

| 周 | 起動（start から最初のコマンドまで） | 取得と checkout | 作り直し全体（merge-base を含む） |
|---|---|---|---|
| 1 | 1347 | 778 | 1671 |
| 2 | 864 | 714 | 1631 |
| 3 | 516 | 785 | 1697 |

手で動かした別の回は、起動 801 / 169 / 240、作り直し 1824〜2011。初回の `wrangler dev` はイメージのビルドと `cloudflare/proxy-everything` の取得で約 10 秒。repo が小さいので、大きな repo の取得時間はこの数字から分からない。

注意点（文書と違った点を含む）:

- **Sandbox SDK 1.0 は形が変わった:** 0.x の `getSandbox()` と `sandbox.exec()` は無くなり、自分の Durable Object が `ctx.container`（`start` / `exec` / `destroy` / `setInactivityTimeout`）を直接使う。`@cloudflare/sandbox` が足すのは `Files`、`S3Mount`、`DirectoryBackup` だけ（パッケージの README）。作業場所のアダプタは `container.exec` に対して書く（`src/workspace.ts`）。
- **token を付ける経路:** `enableInternet: false` にして、`interceptAllOutboundHttp` と `interceptOutboundHttps("*", …)` で全部を `WorkerEntrypoint`（`GitOutbound`、`src/workspace.ts:26`）に通す。github.com のこの repo のパスだけを通し、token は Worker が `Authorization: Basic x-access-token:…` で付ける（`:40`）。`exec` は `start` の環境変数を引き継がないので、git に毎回 `GIT_SSL_CAINFO=/etc/cloudflare/certs/cloudflare-containers-ca.crt` を渡す必要がある。
- **非公開の repo は試していない:** token の注入は形だけで、`GITHUB_TOKEN` を設定していない。公開 repo に対して通過と拒否を確かめただけ。
- 試作では Docker の要る Worker を別の設定（`wrangler.sandbox.jsonc`、入口 `src/workspace-dev.ts`、認証なし）に分けた。本番の 1 つの Worker にまとめるかは決めていない。

## tech-selection.md で直すべき点

1. **PrSession の名前 `owner/repo#n` は `/agents/pr-session/:name` で扱えない。** `routeAgentRequest` は経路の区切りをそのまま名前にし、percent-decode しない（`agents/dist/agent-routing.js:124-127`）。`%2F` や `%23` で送ると `octo%2Fdemo%231` という別の DO になり、webhook 側（`getAgentByName` に `owner/repo#n`）と一致しない。試作は `owner~repo~n` にした（`~` は URL で安全で、GitHub の owner / repo 名に使えない。`src/webhook.ts:10`）。
2. **Sandbox:** 上の「Sandbox SDK 1.0 は形が変わった」。手順（空から作り直す、送信の HTTPS を Worker が受けて token を付ける）は 1.0 でも成り立つ。
3. **GitHub App の鍵は PKCS#8 で保存する**（上の確認 5）。
4. **「待っている質問は次の分析より先」** は、AIChatAgent の turn の待ち行列と、分析を 1 件ずつ渡すことで成り立つ。`waitUntilStable()` はこの場面の決め手ではない。
5. **会話の表示順は保存の順:** 実行中の turn の間の質問はその回答より前に、local の回答は末尾に並ぶ。回答と質問の対応は `metadata` で持つ前提にする。
6. 参考: Node の `WebSocket`（undici）は第 2 引数でヘッダを渡せた（e2e の `ChatClient` はこれで JWT を付けている）。ブラウザーではできない。prq を HTTP の long-poll にする判断は変わらない。
