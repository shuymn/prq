# Prototype checks

What a small prototype checked before the design was fixed, and how the design changed because of it. The code is on the
`spike/prototype` branch (history unrelated to `main`) and is a reference, not a base to merge. Server and CLI checks are
under `packages/` there, the model and compaction checks under `spikes/llm-check/`, and the full Japanese-language
write-ups are `docs/spike-results.md` and `spikes/llm-check/results.md`.

All numbers below are local measurements: a macOS laptop with Docker, Node 24, and calls from a laptop to an LLM API.
None of them is a production value. Nothing was deployed.

## How it was run

- The server tests run inside workerd with `@cloudflare/vitest-plugin`. The end-to-end tests start a real `wrangler dev`
  and the real `prq` CLI from Node, each test file with an empty store. The Sandbox test needs Docker and access to
  `github.com`.
- The chat client in the tests is a Node client speaking the same WebSocket messages as `useAgentChat`; no React UI was
  built.
- Access was replaced by an HS256 JWT verified with `jose`; service tokens were told from users by the `common_name`
  claim. Production uses RS256 with a remote JWK set.
- Where a model was needed in the server tests, the AI SDK's mock model was used. Model behavior was checked separately
  against a real provider.
- The end-to-end suite passed three runs in a row (35 to 45 seconds each).

## Results

| Check | Verdict | Notes |
| --- | --- | --- |
| Local-owner PR session and `prq wait` / `claim` / `submit`, agent IDs | Works, with notes | A UI question became a job without a model turn, `wait` returned it, `claim` and `submit` appended the answer to connected clients. See below. |
| Cloud-owner turn with a mock model | Works, with notes | Streaming over several `text-delta` parts and persistence; webhook analyses appended after `waitUntilStable()` with the function form of `saveMessages`. |
| GitHub App tokens and webhook signature in workerd | Works, with notes | `@octokit/auth-app` and `@octokit/webhooks-methods`. The private key must be PKCS#8. |
| Sandbox rebuild | Works, with notes | Rebuild from empty at a pinned SHA, and git traffic restricted to one repository on `github.com` through the Worker. |
| Tool calling and streaming with an OpenAI-compatible provider | Works | Two models of one provider, with valibot tool schemas. |
| Context compaction | Works under conditions | Earlier decisions and facts survived six compactions. Needed the changes listed below. |

### Local owner, `wait`, agent IDs

Covered and passing: the owner fixed at creation from the pool; presence ending after the timeout and holding during a
long-poll; a UI question reaching `prq` without a model turn; a second question while the first is pending, and a second
after the first is answered; an idempotent resubmit of the same `jobId` + `claimId` (also when concurrent); rejection of
an old `claimId` after a retry; a restarted process with the same agent ID getting its claimed job first with a new
`claimId`; another agent ID never receiving that job; no job loss when the waiter disconnects right after a notification;
a waiting `prq` waking in under 3 seconds when a question arrives; an answer appended while the chat client was
disconnected being readable on reconnect; auth failures (401, 403) ending with their own exit code; and webhook handling
for a local owner (a question runs before an analysis, unstarted analyses fold into the latest head, other people's PRs
and wrong signatures are refused).

To confirm the tests were meaningful, each guard was removed in turn (resubmit result, `claimId` check, resume priority,
new `claimId` on resume, agent ID check) and the matching test failed in each case.

Findings:

- **Not running a turn.** For a local owner, `onChatMessage` returns `undefined`. The SDK logs a warning and sends a
  frame with the text "No response was generated by the agent." and `done: true`. The transport drops a non-JSON body,
  so the screen shows nothing, but the warning appears once per question and should be reviewed before production.
- **Which questions get jobs.** With queued sends, the next question can already be stored when a turn runs, so jobs
  are made for every user question that has none, not for the last message.
- **Order.** `persistMessages` appends at the end: after two waiting questions the order is question 1, question 2,
  answer 1, answer 2. The UI pairs them through the answer's `metadata` (`jobId`, target).
- **Presence.** The prototype counted an agent present from its last contact within the timeout, or during a long-poll;
  it did not cover the whole period between a claim and its submit. The design covers it (up to 60 minutes from the
  claim).
- **Concurrent owner decisions.** The first decision is kept (`INSERT OR IGNORE`).
- **SDK name clash.** A PrSession method named `retry` overrides `Agent.retry`; it is named `retryJob`.
- **Not built:** the 60-minute stalled indication (only the retry API), `prq context`, `checkout`, `reconcile` and the
  local AI's skill file.

### Cloud owner

- A send runs a turn, streams, and is saved. Webhook analyses go through `waitUntilStable()` and the function form of
  `saveMessages`; with A running and B, a question and C arriving, the order was A, question, C and B was superseded.
- Removing the folding of unstarted analyses made B run and the test fail. Removing `waitUntilStable()` did not change
  the result: a waiting question is handled first because AIChatAgent's turn queue is in arrival order and analyses are
  handed over one at a time. The rule keeps `waitUntilStable()` anyway.
- A question sent during a turn is placed before that turn's answer (saved order). A mock that returned "the last
  message" picked up a previous answer, so context assembly must use the last user message, not the last message.

### GitHub App and webhook libraries

- A PKCS#1 key (the format GitHub issues) is rejected with "only PKCS#8 is supported". With PKCS#8 an App JWT is made
  (RS256, `iss` = App ID, lifetime within 10 minutes) and verifies with `jose`; the installation token is requested with
  the App JWT and cached; `X-Hub-Signature-256` matches GitHub's documented test vector and rejects a wrong signature,
  secret, body or an `sha1=` form.
- The only compatibility problem: `universal-github-app-jwt` resolves its crypto module through `imports`, to a Node
  module under Node and to a WebCrypto, PKCS#8-only module elsewhere, which is what workerd gets. The fix is the
  one-time conversion of the key.
- Bundling was checked with esbuild using the `workerd`, `worker` and `browser` conditions; wrangler's own condition list
  was not checked, and there was no deploy or dry run.

### Sandbox

- From empty: `git init`, fetch head and base by SHA with depth 1, check out head, deepen once when no merge-base was
  found. After a stop and a restart the same SHA was checked out and no earlier disk remained. `git grep` and the
  package's `Files.readFile` worked in the checkout.
- Git traffic went only through the Worker's outbound handler: the same repository passed, and another repository, another
  host and plain http returned 403. The target was a small public repository.
- Timings over three rounds (milliseconds): start to first command 1347, 864, 516; fetch and checkout 778, 714, 785;
  whole rebuild including the merge-base step 1671, 1631, 1697. A first `wrangler dev` took about 10 seconds to build the
  image and pull the proxy image. A small repository says little about a large one.
- **Sandbox SDK 1.0 changed shape.** The 0.x `getSandbox()` and `sandbox.exec()` are gone; a Durable Object of our own uses
  `ctx.container` (`start`, `exec`, `destroy`, `setInactivityTimeout`) and the package adds `Files`, `S3Mount` and
  `DirectoryBackup`. The workspace adapter is written over `container.exec`.
- **Token path.** With `enableInternet: false`, all outbound HTTP and HTTPS are intercepted and sent to a
  `WorkerEntrypoint`, which lets through only this repository's path on `github.com` and adds
  `Authorization: Basic x-access-token:…`. `exec` does not inherit the environment of `start`, so git is given
  `GIT_SSL_CAINFO` on every call.
- A private repository was not tried: the token injection exists in form only. The Docker-dependent Worker was kept in a
  separate configuration; whether to merge it into the single Worker is open.

### Tool calling and streaming (OpenAI-compatible provider)

Both models tried called the valibot-defined tools correctly, finished in 4 or 5 steps, and streamed text, reasoning and
tool-input parts. Time to first text was about 0.5 seconds for the smaller model and about 10 seconds for the larger one
(reasoning streams first); total about 8.5 and 13 seconds. Automatic prompt caching showed up as cache-read tokens, so a
continued conversation pays the cached rate for history.

Findings that became rules: an invalid regular expression passed to `grep` came back as a tool error and the model
carried on, so tools return bad input as an error string; without a tool that lists the workspace the model searched for
files that do not exist until the step limit left an empty answer, so a listing tool exists from the start and reaching
the step limit returns what was gathered.

### Compaction

The method follows Pi (`pi-coding-agent`, MIT): usage-based token count plus an estimate, a cut point that keeps recent
messages without splitting a tool call from its result, a separate summary of the first half of a split turn, an updated
rather than rewritten summary, a file list, and insertion as a prefixed message. The sections were purpose, overview of
the change, decisions, the user's interests and preferences, open questions and key facts.

- **Data.** A diff of a public library between two releases: 59 source files, about 180,000 characters, measured at about
  60,000 tokens, read through listing, reading (12,000 characters at a time) and search tools. A 16-turn conversation set
  six decisions in the first six turns (one changed at turn 9) and four facts found in code; later turns read more of the
  diff to grow the context.
- **Probes.** After the conversation, 10 independent questions with tools disabled, scored by keyword match (lenient).
  The baseline kept the same token budget by dropping whole old turns.
- **Runs.** Run 1: window 32k, reserve 4k, keep 8k: one compaction (28,445 → about 7,700 tokens), 13.9 s. Run 2: window
  20k, reserve 3k, keep 6k: six compactions, 13.8 to 23.2 s each (two model calls: the summary and the first half of the
  turn), average turn time 11.3 s.
- **Result.** With compaction, all 10 memory-only probes passed in both runs. The baseline passed 2 of 10 in run 2 (the
  two it passed were stated in a commit list in the system prompt) and 9 of 10 in run 1 (not a fair comparison: the
  baseline there held about 38k tokens against a 32k window because the budget was measured by characters ÷ 4). The
  changed decision was replaced by the new one in the updated notes. The full history hash was unchanged.
- **Limits of the test.** Run 2 stopped in its last probe because of the script's own token ceiling, so its
  per-answer text was not saved (only pass/fail in the log); the small errors seen in run 1 answers were an incorrect
  type name and a reason the user had not given.

What turned out wrong, and what the design does about it:

| Found | Design |
| --- | --- |
| Characters ÷ 4 under-counted Japanese text and diffs by 1.3 to 1.7 times (median 1.49) | Count from the provider's usage and estimate only what was added since, at characters ÷ 3 or a measured ratio |
| One turn can overrun the window through tool results; in run 2 a retry only passed because the model read less | Cap each tool result (12,000 characters) and the amount one turn reads; answer from what was read |
| Notes grew from 3,560 to 13,406 characters over six updates, and the model added interests the user never stated | No size cap (a realistic window compacts only a few times; a summary cut by the output limit is not adopted); "interests and preferences" only from what the user said |
| The summary added reasons nobody gave | "Decisions" in the user's words, a reason only if given |
| Cutting inside a turn happened six times out of six | Summarizing the first half of a split turn is required |
| Compaction costs 14 to 23 seconds | Compact after the answer is returned, not before the next question |
| Reasoning content | Removed from the context when a turn ends; no problem was seen |

Adoption test met: after repeated compaction the model still answered what was decided before.

## What changed in the design

1. The PR session name `owner/repo#n` cannot be a path segment of `/agents/pr-session/:name`, because the router does not
   percent-decode; the name is `owner~repo~n`.
2. Sandbox SDK 1.0's shape (above). The procedure (rebuild from empty, git traffic through the Worker with the token added)
   still holds.
3. The GitHub App key is stored as PKCS#8.
4. A waiting question goes before the next analysis because of AIChatAgent's turn queue and one-at-a-time hand-over of
   analyses, not because of `waitUntilStable()`.
5. The conversation shows saved order; answers are paired with questions through `metadata`.
6. The `prq` ↔ Hub connection stays an HTTP long-poll: a Node WebSocket client can send headers on connect, a browser
   cannot.
7. Compaction parameters and rules above.
